# Codebase Improvement Opportunities

| Area | Finding / Evidence | Impact | Recommendation |
| --- | --- | --- | --- |
| Data source initialization & identity flow | `App` still pulls `petName`/`character` directly from AsyncStorage (`src/app/App.tsx:120`) and calls `initializeDataSource()` without awaiting it before rendering. Screens may render stale identity data when remote mode is active. | Remote profile and navigation can desynchronize from the backend, confusing users when their server-side identity differs from what the UI shows. | Introduce a `PetIdentityProvider` that awaits `initializeDataSource()` and hydrates identity via `LocalDataManager.getPetIdentity()`. Expose a hook (`usePetIdentity`) so all screens consume the same source of truth and can react to mode changes. |
| AsyncStorage sprawl across screens | Components such as `Activities.tsx:25`, `Inventory.tsx:61`, `Hollywood.tsx:43`, `Gym.tsx:39`, etc. keep calling `AsyncStorage` for `petName`, `character`, `oid`, and gameplay stats. These bypass the new data-source abstraction. | Remote mode cannot fully work because UI keeps reading stale local values; future schema changes require editing dozens of files. | Refactor components to consume a single state store (context/Zustand) that delegates to `LocalDataManager`. Audit `rg "AsyncStorage"` to eliminate direct usage outside shared utilities. |
| Remote inventory sync | `updateInventoryItem` derives the remote delta from the cached quantity (`src/utils/LocalDataManager.ts:222`). If the cache is stale, the request sends an incorrect delta and can underflow server validation. | Inventory counts drift between client and backend, causing failures or inconsistent UX when multiple devices/users interact. | Add API support for both `set` and `increment` operations, or re-fetch the item before calculating the delta. Consider optimistic updates with rollback on failure. |
| Axios client reuse & observability | `petApiClient` creates a new Axios instance per call (`src/services/petApiClient.ts:52`), so interceptors, retries, logging, and auth headers must be duplicated. | Harder to add cross-cutting concerns (auth, tracing). Network bugs are harder to debug without centralized middleware. | Export a singleton Axios client configured once (base URL, timeouts, interceptors). Wrap API methods with typed helpers that share this instance. |
| Configuration & mode toggling | `API_BASE_URL`/`DATA_SOURCE_MODE` are hardcoded constants in `config.ts:1`. Switching modes or pointing at staging requires editing source and rebuilding. | QA/devs cannot toggle between local and remote setups quickly; mistakes happen when commits accidentally ship with “remote” defaults. | Read configuration from `.env`/Metro settings and expose a developer toggle (e.g., Dev Menu switch) that calls `setDataSourceMode`. Persist the choice via `AsyncStorage` so testers can switch without code changes. |
| Testing & error handling gaps | No automated tests cover `LocalDataManager` or the new remote flow; errors (e.g., failed profile creation) are only logged in `console.error` and surface to users as silent failures (`src/app/App.tsx:104`). | Regressions in the data-source layer could ship unnoticed; users won’t know why profile creation failed. | Add Jest unit tests mocking `isRemoteMode()` to verify both local and remote code paths. Surface API failures via UI toasts/modals with retry options, and consider a telemetry hook for backend errors. |
